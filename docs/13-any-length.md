# 13. 턴 수와 무관한 기억 — 5,000 · 10,000 · 1,000,000턴

## 요구

1,000턴은 통과 기준이 아니라 첫 눈금이다. 관계가 5,000턴, 10,000턴, 1,000,000턴이 되어도 캐릭터는 같은 사람이어야 하고, 1턴에 들은 것을 999,999턴 뒤에도 물으면 답할 수 있어야 한다. 그러려면 **프롬프트에 들어가는 양이 턴 수와 무관해야 하고(O(1)), 나머지 전부는 디스크에 있어야 하며, 꺼내는 것은 모델이 읽어서 득이 되는 것만이어야 한다**(12의 결과 2·3: 많이 보일수록 깎였다).

## 지금 구조가 깨지는 지점 (잰 것과 외삽)

| 구성 | 1,000턴(실측) | 5,000 | 10,000 | 1,000,000 |
|---|---|---|---|---|
| 장부 25칸 | 사실은 안 버렸지만 칸이 문단이 됨: 374 → 9,041자, 프롬프트 토큰 +75% | 요약기가 자르기 시작할 것. 상한은 개수지 글자가 아니라서 | 깨짐 | — |
| archive(메모리 배열) | 2,480~2,736개(턴당 2.7개) | 1.4만 | 2.7만 | **270만 개**, e5 임베딩 float32 384차원 = 1.5KB/개 → 4GB. 프로세스 안에 못 둔다 |
| 벡터 질의(전수 코사인) | 7~53ms | ~70ms | ~130ms | 측정: 10만 개 240ms(node:sqlite BLOB → Float32Array) → 270만 개 **약 6.5초**. 전수는 안 된다 |
| 채점기 근거(유저 발화 전문) | 79k자, 상한 120k | 400k자 → 상한 초과 | — | — |
| 실측 시간(CLI 구독, 답장당 ~7초 + 요약) | 6~7시간 | ~35시간 | ~70시간 | ~290일. 직접은 못 잰다 |

1,000턴에서 장부가 29개 중 28개를 들고 있었던 것은 **칸을 문단으로 키워서**였다. 그 방법은 글자 예산이 없어서 가능했고, 그래서 토큰이 75% 늘었다. 같은 방법이 5,000턴에서 되풀이되면 프롬프트가 캐시를 넘고 응답 시간이 다시 밀린다. 즉 12의 "장부가 잘 버텼다"는 1,000턴에서만 참이다.

## 설계

### 원칙

- **프롬프트는 O(1).** 장부(개수 + 글자 예산), 계층 요약(현재 장·현재 계절), 꺼낸 것(있을 때만, 한 주제).
- **규칙은 메커니즘에만.** 무엇이 사실이고 무엇이 바뀌었는지는 요약기(모델)가 적고, 저장소는 그것을 색인하고 예산을 지킨다. 단어 목록(요일·보통명사 제외)은 쓰지 않는다. 대신 통계로 거른다(아래 "태그의 질").
- **디스크가 진실.** 세션 객체는 캐시다. 프로세스가 죽어도, 1년 뒤 다시 와도, 파일 하나에서 이어진다.

### 1. 영속 저장소: SQLite 파일 하나

Node 22에 내장된 `node:sqlite`를 쓴다. 네이티브 의존성·서버·도커 없이 clone 후 바로 돌아야 하고, 수백만 행은 SQLite의 일상 범위다. 캐릭터–유저 쌍마다 파일 하나.

```
turns          (idx, role, content, at)                         -- 전사 전문
facts          (id, text, source, turn_from, turn_to, status,  -- archive. status: current | superseded
                superseded_by, embedding BLOB)
entities       (name, kind, n_facts, first_turn, last_turn)    -- 노드
fact_entities  (fact_id, entity, role)                         -- 간선: 사실 ↔ 고유명사 (role: subject | object | mention)
summaries      (level, turn_from, turn_to, text)               -- 0: 통합 요약, 1: 장(~100턴), 2: 계절(~1,000턴)
ledger         (turn_to, json)                                 -- 장부 스냅샷
```

벡터 색인은 따로 두지 않는다. **질의는 항상 좁힌 뒤에 한다**(아래 4). 좁힌 후보가 10만 개를 넘는 일이 생기면(측정 240ms) 그때 HNSW를 붙인다. 지금 붙이지 않는 이유는 12와 같다. 필요가 측정되기 전에 부품을 늘리지 않는다. Postgres/pgvector는 같은 인터페이스 뒤에서 바꿔 끼울 수 있게 `MemoryStore`로 감싼다.

### 2. 장부에 글자 예산

25칸에 더해 전체 글자 예산(처음 2,000자)을 둔다. 요약기 프롬프트에 예산을 적고, 넘치면 저장소가 가장 오래 갱신되지 않은 칸부터 archive로 내린다(`status: current` 그대로, 장부에서만 빠짐). 1,000턴 실측에서 9,041자였으니 처음부터 깎이는 것이 보일 것이고, 그래서 **꺼내기가 메울 구멍이 생긴다**. 12의 실험 설계 결함(얻을 자리 한 칸)을 이것으로 고친다.

### 3. 계층 요약

지금의 통합 요약(10턴마다 갱신)은 level 0. 100턴마다 level 0 열 개를 한 장으로(level 1), 1,000턴마다 장 열 개를 한 계절로(level 2). 프롬프트에는 **현재 계절 + 현재 장 + 장부**만 들어간다. 1,000,000턴이면 계절이 1,000개지만 프롬프트에는 하나다. 지난 계절은 꺼내기의 대상이다.

### 4. 그래프와 꺼내기: "주제 한 장"

12에서 틀린 것은 꺼내는 **단위**였다. 흩어진 사실 top-5는 잡음이고, 보일 때마다 캐릭터가 따졌다. 단위를 **고유명사 한 장(entity page)** 으로 바꾼다. 보리에 대해 아는 모든 것을 시간순으로, 바뀐 것은 `superseded`로 표시해서("처음엔 아메리카노 → 1,713턴부터 라떼"), 각 줄에 시점을 달아서.

- **그래프의 간선은 요약기가 적는다.** `new_facts`에 `subject`·`object`를 받는다(판단은 모델). 저장소는 `fact_entities`에 넣고 센다. 이것이 지식 그래프의 전부이고, Neo4j가 필요한 질의(다중 홉)는 이 제품에 없다. 있으면 그때 잰다.
- **트리거는 기계적이다.** 유저의 이번 말에 저장소가 아는 고유명사가 있는데 **장부 본문에 없으면** 그 장을 꺼낸다. "기억나세요?"를 규칙으로 잡지 않는다. 장부에 있는 것은 이미 보이므로 꺼내지 않는다(12의 1976턴이 정확히 이 경우였다: 하늘 동물병원이 archive에는 16개, 장부에는 없음).
- **고유명사가 없는 질문**("그때 뭐라고 하셨죠?")은 벡터로 가되, 후보를 먼저 좁힌다: 최근 장부·현재 장에 등장한 고유명사의 사실들 ∪ 지난 계절 요약들. 전수 코사인은 없다.
- **보이는 양의 상한**: 한 턴에 장 하나, 줄 수 상한(처음 8). 두 고유명사가 걸리면 장부에서 더 오래 빠져 있던 쪽.

### 5. 태그의 질 (12의 결과 3)

요약기가 금요일·아메리카노·골목·카운터를 고유명사로 달았다. 두 가지로 고친다. 요약기 프롬프트에 "사람·장소·이름 있는 사물·고유한 날짜만, 요일·일반 명사는 아님"을 적고(모델의 판단), 저장소는 **변별력으로 거른다**: 전체 사실의 일정 비율(처음 5%) 넘게 달린 태그는 트리거에서 뺀다(통계, 단어 목록 아님). 두 화자의 이름은 그 규칙에 자동으로 걸린다(하루 15%, 민수 18%). 호칭 접미사("하루 씨")는 이미 벗긴다.

### 6. 바뀐 사실

archive는 append-only였다. `status`를 더해 요약기가 "바뀌었다"고 적은 사실은 옛 것을 `superseded`로 표시하고 `superseded_by`로 잇는다(판단은 모델, 표시는 저장소). 장에서는 둘 다 보이되 옛 것은 "~였다"로. 1,000턴의 라떼 반전(1,713턴부터)이 첫 시험대다.

## 측정 계획: 290일 없이

**A. 저장·검색 계층 단독 (모델 없음, 시간 단위).** 실제 archive 2,700개를 종자로 고유명사·숫자·날짜를 치환해 270만 개를 만든다(10,000턴 = 2.7만, 100,000턴 = 27만, 1,000,000턴 = 270만). 잰다: 적재 시간, 파일 크기, 고유명사 장 조회, 좁힌 벡터 질의, 전수 벡터 질의(비교용), 프로세스 메모리. 통과선: 장 조회 50ms 이하, 좁힌 벡터 질의 100ms 이하, 메모리는 턴 수와 무관.

**B. 대화 품질, 구멍이 있는 조건에서 (1,000턴 재생, 7시간).** 같은 유저 턴(long-run-1000)을 재생한다. arm: ① 장부 25칸 글자 예산 없음(12의 기준선), ② 장부 10칸 + 예산 1,000자, 꺼내기 없음, ③ ②에 주제 한 장 꺼내기. ②가 ①보다 프로브를 잃어야 실험이 성립하고(구멍), ③이 그것을 되찾되 기억·이탈이 ①보다 나쁘지 않아야 한다. 12에서 못 잰 "꺼내기의 값"이 여기서 나온다.

**C. 5,000턴 한 번 (35시간).** 비트 50개짜리 시나리오를 생성기로 만든다(비트 풀 + 시간 진행 + 바뀌는 사실 10개 + 프로브 60개, 거리 최대 4,500턴). 채점기는 유저 발화 전문 대신 **저장소에서 뽑은 근거**(프로브의 고유명사가 든 유저 턴만)를 받는다. 그래야 채점이 턴 수와 무관해진다. 10,000턴 이상은 A로 대신하고, C의 5,000턴 곡선(1,000턴 단위 기억 점수)이 평평하면 "턴 수와 무관"의 증거로 삼는다.

## 순서

1. 저장소(SQLite) + 기존 archive 적재 + A 벤치 → 2. 장부 글자 예산 + 계층 요약 → 3. 그래프 간선 + 주제 한 장 꺼내기 + 태그 변별력 + 바뀐 사실 → 4. B(1,000턴 재생) → 5. 시나리오 생성기 + 채점기 근거 변경 → C(5,000턴).
