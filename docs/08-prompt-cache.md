## 문제

답장 한 번의 원가는 프롬프트 토큰이 지배하고(`01`), 프롬프트 토큰의 원가는 캐시 적중률이 지배한다(캐시 읽기는 정가의 1/10). 50턴 대화에서 답장당 프롬프트는 1만 토큰 안팎인데, 그중 얼마가 캐시에서 오는지는 프롬프트의 **어느 부분이 매 턴 바뀌는가**에 달려 있다. 이 저장소의 실행 경로(Claude Code CLI, `claude -p --system-prompt`)에서 캐시가 어떻게 동작하는지 실측했다.

## 측정

답장마다 기록된 캐시 토큰을 50턴에 걸쳐 보면 규칙이 바로 드러난다.

| arm | 캐시 적중 답장 | 캐시 미스가 난 답장 번호 | 캐시된 토큰 | 프롬프트 중 캐시 비율 |
|---|---:|---|---:|---:|
| v3-structured (하루) | 41 / 50 | 1, 15, 20, 25, 30, 35, 40, 45, 50 | 3,449 → 5,305 (증가) | 47% |
| v3-structured (카엘) | 42 / 50 | 1, 20, 25, 30, 35, 40, 45, 50 | 4,008 → 6,500 | 42% |
| v3-recent (RECENTLY SAID를 시스템 프롬프트 안에) | **0 / 50** | 전부 | 0 | **0%** |
| v2-full-transcript (창 400턴) | – | – | 3,430 | 18% |

세 가지가 읽힌다.

1. **캐시되는 것은 시스템 프롬프트 전체이고, 바이트 단위로 같을 때만이다.** 캐시된 토큰 수는 시스템 프롬프트 크기와 일치하고, 기억 블록에 사실이 쌓일수록 같이 커진다.
2. **미스는 정확히 기억 요약이 갱신되는 턴에 난다.** 10턴마다(답장 15, 20, 25…) MEMORY 블록이 바뀌고, 그 턴의 시스템 프롬프트는 통째로 다시 과금된다. 50턴에 8~9번, 프롬프트 토큰의 약 10%.
3. **매 턴 바뀌는 블록을 시스템 프롬프트에 넣으면 캐시가 0이 된다.** 재생성 실험 3라운드(`04`)에서 "직전 3답장의 요지"를 시스템 프롬프트 안에 넣은 `v3-recent`는 50턴 내내 캐시 0이었다. 품질은 v3보다 좋았지만(일관성 +0.3, 말투 +0.2) 프롬프트 원가가 두 배가 넘는 셈이라 그대로는 쓸 수 없다.

전사(transcript)는 CLI 경로에서는 캐시되지 않는다. stdin으로 들어가는 유저 메시지 한 덩어리라 브레이크포인트를 둘 수 없다. 프롬프트의 절반이 넘는 부분이고, 이것이 CLI 경로의 구조적 한계다.

## 수정: 상태는 시스템 프롬프트 밖으로

엔진의 메시지 타입에 `kind: "context"`를 추가했다. 프롬프트 빌더는 정적인 지시(정체성, 세계, 말투, 형식, 경계)만 시스템 메시지로 내고, 매 턴 바뀌는 상태(관계 단계, 기억 요약과 사실, 직전 답장 요지)는 컨텍스트 메시지로 낸다. CLI 어댑터는 컨텍스트 메시지를 `--system-prompt`가 아니라 stdin 프롬프트 머리에 `[CURRENT STATE]`로 접는다. OpenAI 호환 어댑터는 두 번째 시스템 메시지로 보낸다(접두 캐시는 첫 시스템 메시지까지 유지된다).

| 버전 | 시스템 프롬프트 | 컨텍스트 메시지 |
|---|---|---|
| `v3-structured` | 전부 (기억 포함) | 없음 |
| `v3-cached` | 정적 블록만 | 관계 단계 + 기억 |
| `v3-recent` | 정적 블록만 | 관계 단계 + 기억 + 직전 3답장 요지 |

사전 예상: 시스템 프롬프트가 대화 내내 바이트 단위로 같아져 50턴 모두 캐시 적중. 대신 기억 블록(500~1,500토큰)이 캐시 밖으로 나가므로 턴당 캐시 토큰은 조금 줄고, 미스 턴의 통째 과금은 사라진다. 50턴에서는 비슷하게 나올 수 있고(미스 9회 × 5k ≈ 매 턴 1k × 50), 차이가 커지는 쪽은 (a) 상태 블록이 매 턴 바뀌는 설계(`v3-recent`)와 (b) API 직접 호출에서 전사 앞까지 캐시 브레이크포인트를 둘 수 있을 때다. 아래 실측은 이 예상의 앞부분을 뒤집었다.

## 실측 (v3 vs v3-cached, 같은 유저 턴 리플레이, sonnet, 50턴)

| | v3-structured (상태가 시스템 프롬프트 안) | v3-cached (상태를 컨텍스트 메시지로) |
|---|---:|---:|
| 캐시 미스 답장 (하루 / 카엘) | 9 / 8 (첫 답장 + 기억 갱신 턴) | **1 / 1** (첫 답장만) |
| 캐시 비율 | 47% / 42% | 40% / 35% |
| 답장당 비캐시 프롬프트 토큰 | 4,321 / 6,295 | **5,119 / 7,301** (+18%, +16%) |
| 답장당 출력 토큰 (CLI 보고) | 380 / 492 | 622 / 611 |
| 답장 길이 중앙값 (글자) | 156 / 203 | 153 / 191 |
| 일관성 / 기억 / 말투 / 회상 | 4.6 / 4.2 / 4.3 / 83% | 4.5 / 4.4 / 4.3 / 83% |

**CLI 경로에서는 분리가 손해다.** 예상대로 미스는 사라졌지만(50턴에 1번), 기억 블록이 캐시 밖으로 나간 비용이 미스 9번을 없앤 이득보다 컸다. 답장당 비캐시 토큰이 16~18% 늘었다. 매 턴 1천 토큰씩 50번 내는 것이 5천 토큰을 9번 내는 것보다 비싸다. 품질은 같다(모든 지표가 노이즈 안).

**출력 토큰이 60% 늘었는데 답장 길이는 같다.** CLI가 보고한 출력 토큰은 622 대 380인데 글자 수 중앙값은 153 대 156이다. 유저가 보는 답장은 같은 길이인데 과금되는 출력이 1.6배라는 뜻이고, 가장 그럴듯한 설명은 프롬프트 머리에 붙은 `[CURRENT STATE]` 블록이 모델의 보이지 않는 추론 토큰을 유발한다는 것이다. 확인하지 못한 가설이지만, 비용에는 그대로 반영된다.

따라서 CLI 경로의 기본값은 **상태를 시스템 프롬프트 안에 두는 v3/v4**로 유지한다. 분리 설계(`v3-cached`)가 이기는 조건은 두 가지뿐이다. (1) 상태가 매 턴 바뀔 때 — `v3-recent`처럼 직전 답장 요지를 넣으면 시스템 안에서는 캐시 0%, 분리하면 35~40%. (2) API 직접 호출로 전사 앞에 브레이크포인트를 둘 수 있을 때 — 그때는 상태 블록이 어디 있든 캐시되지 않는 부분은 마지막 턴뿐이라 분리가 품질·구조상 더 깨끗하다.

이 실험의 교훈은 "좋아 보이는 설계도 실행 경로의 캐시 규칙 위에서 측정해야 한다"는 것이다. 설계 노트만 보면 분리가 당연히 이기고, 실측은 반대였다.

## API 경로에서의 설계

CLI 경로의 한계를 넘어서는 설계는 명확하다. Anthropic API의 `cache_control` 브레이크포인트를 (1) 정적 시스템 프롬프트 끝, (2) 전사의 마지막 유저 턴 직전, 두 곳에 둔다. 그러면 매 턴 새로 과금되는 것은 "마지막 유저 턴 + 컨텍스트 메시지"뿐이고, 50턴 대화의 캐시 비율은 42%에서 90% 안팎으로 올라간다. 기억 블록을 컨텍스트 메시지로 분리해 둔 것은 그때 그대로 쓰인다. 어댑터는 `providers/` 아래에 하나 더 추가하면 되고, 평가 하네스는 스펙 문자열만 바꿔 같은 실험을 돌린다.

## 한계

- 캐시 비율은 CLI가 보고하는 `cache_read_input_tokens`로 계산했다. CLI의 고정 접두(830토큰)도 포함된다.
- 품질 비교는 리플레이 2대화. 배치 설계 변화가 답장 품질에 영향이 없다는 가설은 확인됐다(모든 지표 노이즈 안).
- 출력 토큰 +60%의 원인(보이지 않는 추론 토큰 가설)은 CLI가 세부 사용량을 노출하지 않아 확인하지 못했다. API 경로에서 `usage` 세부 항목으로 검증할 수 있다.
